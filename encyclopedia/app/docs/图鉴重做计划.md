# es-web 图鉴系统重做 · 完整工作计划

> 目标：重做现有「图鉴」（旧 ENCY 数据零散、命名混乱、无筛选无体系），参考 fandom 英文 wiki 等完整站点的卡面图鉴 UI，建立**五星 + 四星卡面图鉴**；每张卡面带 **中文 / 英文 / 日文** 三语卡名。
> 总原则：**先定方案 → 先出小样确认 → 再批量 → 最后集成部署**，把返工和额度消耗压到最低。

## 一、现状盘点（已完成调研）

### 1.1 现有工程（root index.html = v2.9.26，2.81 MB 单文件）
- 现有「图鉴」= `ENCY` 数组（约 2322 行起）：仅 8 个角色、每人 1–2 张卡；`name` 中日英混杂、`star` 为文本星串、缺统一三语、无筛选/搜索卡面能力、仅 2 列小图。判定为本次重做对象。
- **可直接复用、不返工的资产**：
  - 主题变量：`--acc #f0a`（品红）、`--acc2 #2563c9`、浅色背景 `#f2f4fa`、圆角卡片体系。
  - 星级配色现成：`.star5` 金 `#e8a33d`、`.star4` 紫 `#a678d8`、`.star3` 蓝 `#5a9bd6`。
  - 图片放大机制 `openZoom(img)` / `data-zoom`；`es-tab` 视图切换框架；顶部搜索路由。
  - 角色头像 `window.ES_HEADS`（base64）、角色名映射 `ES_ROLE_NAMES`、歌曲 `ES_SONGS`（含组合 `u`、成员全名 `i`）；`buildIdolGroups()`（约 1722 行）按主组合曲出现次数推导「组合→成员」，是**组合归属的权威来源**。
  - **命名/归属红线**：旧 `ENCY.unit` 不可直接沿用（已发现 `mao 衣更真绪` 被旧图鉴标成 MaM，正史/歌曲成员表实为 Trickstar；`kanna` 旧数据甚至未填 unit）。正式版角色规范中文名、日文名、组合归属一律以 `buildIdolGroups()` + `ES_ROLE_NAMES` 为准；fandom wiki 只补卡面英/日文名与 Acquiring 来源，不决定角色归属。
  - **队长（leader）**：仓库内无任何队长/leader 记录（已全文检索为 0）。正式版队长需按官方/fandom 组合页核实后写入 `leader`；未核实前界面只留「队长位·待核实」占位，**不臆断人名**。
  - `assets/cards/` 已有约 14 张本地卡图，可并入新图鉴。
- **保持不动、降低回归风险**：歌曲库、服装（MV Outfits）页、账号所持卡（localStorage 录入）页、排期/时间线/术语页。新图鉴只替换「图鉴」这一视图的卡面部分。

### 1.3 已知卡点与对策
- **卡点 A：卡面页 URL 清单难批量导出**（分类页被拦、角色 Cards 网格链接被脱敏）。
  对策：小样阶段先打通「**单角色 → 逐张详情页采集**」流程；角色详情页 URL 固定为 `/<Role>/<Role>_Cards` 风格；卡面详情页 URL 形如 `(English Name)_Role`。先用已确认的 fandom 链接（旧数据里已有 5 条真实 fandom 卡面链接）跑通，再按角色扩展。采集以**可控小批**推进，不追求一次性全量。
- **卡点 B：全量规模大**（全角色五星+四星估计数百张，单会话无法采完）。
  对策：分期交付，首批「小样 + 1 个组合」，其余按组合分批追加；UI/数据模型一次定型，后续只增量灌数据，不返工界面。
- **卡点 C：高清卡面图获取受限（2026-11-02 实测）**：详情页 web_fetch 只给文字；角色 `/Cards` 网格页只给 100×125 低清缩略（能核对角色/星级/组合，但无法唯一配对卡名、放大即糊，不进正式网格）；高清带框图（约 640×800）原图域 SSL 不通、内置浏览器后端不可用。
  对策：①正式网格先以「三语卡名 + 来源档期 + 图位占位」定型，高清图网络恢复后只填 `img` 字段、不返工界面；②低清缩略仅放小样核对区验证角色/星级不拿错；③解锁条件＝本机经代理可访问 wikia 原图/GitHub raw，或用户提供按命名整理的图包；④配对纪律：缩略顺序必须与详情页文字交叉确认后才绑定卡名，禁止凭低清猜卡名。
- **卡点 C2（增量，不影响首版）**：fandom 默认是带框（开花满破）版；若后续要无框（Frameless），在详情页 Gallery 区补采。

## 二、新图鉴设计方案（方案确认后再做小样）

### 2.1 数据模型 `window.ES_CARDS`（一次定型，后续只追加）
```
{
  id: "raika_lyrical",        // 稳定 id = 角色英文短名_序列
  roleEn: "Raika",            // 角色英文/罗马音
  roleJp: "ライカ",
  roleZh: "莱卡",             // 角色中文名（沿用 ES_ROLE_NAMES / 国服名，缺则补译）
  unit: "Special for Princess!",
  star: 4,                    // 4 / 5（数字，便于排序筛选；展示为 ★★★★）
  en: "Lyrical White",        // 英文卡名（fandom 标题）
  jp: "リリカル・ホワイト",    // 日文卡名（fandom 方括号内原文）
  cn: "抒情纯白",             // 中文卡名（国服官方译名优先，否则意译；意译项加 *）
  bloom: true,                // 是否开花版（默认 true；未开花另存 bloom:false）
  img: "assets/cards/cards/raika_lyrical.jpg",
  srcType: "scout",           // 获取来源类型：scout=卡池 / event=活动 / other
  srcName: "Cross Scout・Ambivalence／inspired", // 卡池或活动名（fandom Acquiring）
  srcDate: "2025-04-25 ~ 05-10",                 // 开启时间（活动/卡池档期）
  source: "fandom wiki",      // 数据站点标注
  link: "https://ensemble-stars.fandom.com/wiki/(Lyrical_White)_Raika"
}
```
- 命名规则：图文件名 `角色短名_序号.jpg`，统一放 `assets/cards/cards/`；`cn` 与 `en`/`jp` 缺失时留空并在小样/数据清单标注，**不编造**。
- 角色主数据 `ES_ROLE_META`：`{key, zh, jp, en, unit, leader:boolean, avatar?}`；`leader=true` 者在组合内置顶并打金色队长徽标；成员 `zh/jp/unit` 取自仓库 `ES_ROLE_NAMES` / `buildIdolGroups()`，不照抄旧 ENCY。
- 组合元数据 `ES_UNIT_META`：`{unit, sub(日文/别称), color, leaderKey}`；`leaderKey` 未核实为 `null`（界面显示「队长位·待核实」占位，核实后替换）。
- 卡模型 `ES_CARDS` 用 `role`（对应 ES_ROLE_META.key）关联角色，避免角色名在卡数据里重复写错。

### 2.2 信息架构（两层：组合 → 角色；参考 fandom 卡面图鉴，最终口径以小样 v0.5 为准）
1. **顶部工具条**：搜索框（同时匹配 中/英/日卡名、角色名、组合名）+ 实时计数（命中张数 / 5★ / 4★）；星级不作为主筛选，改在角色页内分区呈现。
2. **一级 · 组合块（默认视图）**：
   - 每个组合一个卡片块：组合名 + 日文别称 + 成员数、5★/4★ 计数；
   - 块内**逐人展示该成员自己的最新一张卡面**（最新 = 已采集 ready 优先 → 星级高优先 → 档期新优先）；
   - **成员排序：队长固定第一位**（金色「队长」徽标），其余按仓库成员顺序；
   - 成员卡显示：最新卡星级角标、角色中/英/日名、最新卡名、`5★n / 4★m` 计数；点击进入该角色页。
3. **二级 · 角色详情页**：
   - 返回组合列表；角色头（三语名、组合、队长徽标、5★/4★ 计数）；
   - **五星区、四星区分开两个标题网格显示**（★★★★★ 五星卡面 n 张 / ★★★★ 四星卡面 m 张）；
   - 卡面卡片：3:4 竖图、星级角标、中文卡名（加粗主名）+ 英文 + 日文、**获取来源行（卡池=蓝标 / 活动=橙标 + 名称 + 档期日期）**。
4. **交互**：点卡 → 详情弹窗（所属组合、角色、星级、三语全名、卡池/活动来源与档期、fandom 原文链接、备注）；搜索即时过滤；空区显示「暂无该星级卡面（待采集）」。
5. **空数据策略**：未采集角色/队长位先占位（虚线框 + 待采集/待核实文案），不白屏、不编造卡名与人名。

### 2.3 视觉规范（沿用现有浅色亮主题，不另起配色）
- 卡片白底、细边、圆角 10px；悬浮轻微抬升；5★ 角标金边、4★ 角标紫边；网格桌面 4–5 列、平板 3 列、手机 2 列（现有手机端 2 列延续）。
- 字体层级：卡名 13–14px、英/日名 11–12px、角色组标题 15px 加粗；避免大色块花哨，保证手机端可读性。

### 2.4 与旧功能的边界
- 「服装 / MV」「账号所持卡」保留原逻辑；新「图鉴 · 卡面」专注 5★/4★ 卡面图鉴。
- 旧 `ENCY.outfits` 若含服装图，迁移到服装视图，避免数据丢失；旧 `ENCY.cards` 真实图片与 link 迁入 `ES_CARDS`。

## 三、分阶段实施（含确认点，控返工）

### 阶段 0：方案定稿（当前阶段）
- 产出：本计划；数据模型字段；UI 线框说明。
- 确认点：用户认可「数据模型 + 分组/筛选/三语命名 + 首批范围」后进入小样。

### 阶段 1：静态 UI 小样（先给用户看效果，不碰主工程）★最省返工的关键一步
- 独立文件 `sample/cards_sample.html`（可直接双击打开，已迭代到 v0.6）：两层视图——一级组合块逐人显示最新卡面、二级角色页五星区/四星区分开；含搜索、计数、来源徽标、详情弹窗、移动端响应式；内置 2 张确证 5★ 文字数据 + 待采集占位卡位（不编造卡名/队长名）；底部「图片核对区」放 1 张高清 3★ 真图 + 3 张 HiMERU 5★ 低清参考图，仅用于核对角色/星级，不绑定卡名、不进正式网格。
- 同时给出《采集数据清单样例》（字段、命名、中文翻译示例）供确认翻译口径（国服名优先 / 意译加 `*` 规则）。
- **确认点：视觉风格、三语排版、星级角标、首批组合选择、中文翻译口径** → 确认后才继续，避免改主工程后推倒重来。

### 阶段 2：打通采集管线（程序化、可复用）
- 固定单角色采集流程：
  1. 定位角色 fandom 卡面页；2. 逐张取详情：英名 / 日名 / 星级 / **Acquiring 卡池或活动名 + 档期日期（scout/event 分类）** / 数据站 link；3. 下载卡面图到 `assets/cards/cards/` 统一命名；4. 翻译 `cn`（国服译名优先，fandom 简体名次之，否则意译加 `*`）；5. 生成 `ES_CARDS` 数据行并做自检（图存在、字段齐全、无重复 id、星级正确、来源类型与名称非空）；6. **归属与队长核对**：角色 `zh/jp/unit` 对回仓库 `ES_ROLE_NAMES` / `buildIdolGroups()`，发现与旧 ENCY 冲突以仓库为准；队长 `leaderKey` 经官方/fandom 组合页核实后才置位，未核实保持 null 占位。
- 先跑通 1 个角色、再 1 个组合；输出《采集脚本与字段口径说明》，保证后续批次一致。

### 阶段 3：首批组合批量入库（小样确认后增量推进）
- 按组合分批（建议首批：已有素材最齐的组合起步，如 HiMERU/Raika/Kanna/Jun/Mao/Kanata 所在的 NEW DIMENSION / Crazy:B 小圈，或用户指定组合）。
- 每批：采集 → 本地清单核对（数量、星级、三语齐全度）→ 标注缺图/缺名项。
- 产出 `ES_CARDS` 数据片段与图片文件夹，先不污染主文件。

### 阶段 4：集成进主工程 `index.html`
- 注入 `ES_ROLE_META` + `ES_CARDS`；新增图鉴视图渲染（网格/筛选/搜索/分组/放大）；替换旧 `renderEnc` 卡面区；保留服装与账号页；导航标签文案调整（如「图鉴 · 卡面」）。
- 图片用相对路径 `assets/cards/cards/`；新增 CSS 挂到现有样式区，主题复用。

### 阶段 5：本地验证（交付前强制）
- 本地打开：桌面 + 手机宽度两列；筛选/搜索/放大交互；每张图可显示、无裂图；三语名无错位；旧功能（歌曲、服装、账号、排期）不报错。
- 数据核对：抽样 10 条对回 fandom 原文（英/日名、星级）；图片字节数非零、id 唯一；缺字段清单列出。

### 阶段 6：文档更新与部署
- 更新 `PROJECT-NOTES.md`：新数据模型、卡面采集口径、图片目录、版本号、未完成清单（哪些角色/星级待补）。
- 部署：经 GitHub Contents API 更新根 `index.html` + `versions/<新版本>/index.html`；API 抖动时重试退避；公开仓库不写入 token；先本地成品交付，网络稳定再推 Pages。

## 四、省额度 / 少返工的具体措施
1. **界面一次定型**：静态小样先行，用户确认后再写主工程，避免大段 UI 反复改。
2. **数据与界面解耦**：`ES_CARDS` 纯数据数组，后续灌数据不碰渲染代码；每批独立可回滚。
3. **复用现成资产**：主题色、星级色、放大弹窗、搜索路由、角色头像、已有 14 张卡图，不重造。
4. **分批采集、小步核对**：一个组合一验收，问题早发现，不把错误复制到全量。
5. **只读探查最小化**：主文件只精读关键区段；不整文件反复读取；采集脚本化、可重跑。
6. **明确不做**：首版不做卡面数值（Da/Vo/Pf）、不做无框版、不做账号绑定卡面的新逻辑、不动其他既有页面；这些列为后续增量。

## 五、验收标准
- 两层导航成立：一级组合块内**逐人显示最新卡面、队长置顶**；二级角色页**五星、四星分区显示**；关键词可搜中/英/日卡名、角色名、组合名；
- 每张 5★/4★ 卡面 = 清晰卡图 + 三语卡名（cn/en/jp）+ 星级标识 + **获取来源（卡池/活动名 + 档期日期，区分 scout/event）**；
- **命名一致性**：角色中/日文名与组合归属与仓库 `ES_ROLE_NAMES`/`buildIdolGroups()` 一致，不出现旧图鉴式错挂组合；队长未核实前不写死人名；
- 桌面与手机布局可用，点卡进详情弹窗；旧页面（歌曲、服装、账号、排期）功能不受影响；
- 数据有来源、缺项透明标注、不编造；小样确认后采集的批量数据与小样同口径。

## 六、待用户确认的关键选项（进入小样前一次性确认）
1. 首批采集范围：先做哪 1 个组合 / 哪几名角色作为小样（默认从已有 fandom 链接的 6 人起步）？
2. 中文卡名口径：国服官方译名优先；无官方译名时由我意译并加 `*`，是否认可？
3. 首版是否只要「开花版（满破带框图）」，未开花/无框版后续再补（推荐，省额度）？
4. 图鉴在导航中沿用现有「图鉴」入口替换，还是新增独立「卡面」入口？（推荐沿用「图鉴」替换卡面区，服装另留入口）
